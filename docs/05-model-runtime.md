# Model Runtime — детальное ТЗ (C++/CUDA + Python)

Репозитории: `sovalune-model-runtime` (C++/CUDA, инференс),
`sovalune-training` (Python, обучение).

## 1. Разделение ответственности

| | Model Runtime (C++/CUDA) | Training Pipeline (Python) |
|---|---|---|
| Задача | Онлайн-инференс, tool-calling loop, стриминг токенов | Оффлайн: fine-tuning, оценка, генерация датасетов |
| Hot path | Да — латентность критична | Нет — batch job |
| Общается с Core через | NATS (`inference.*`, `tools.*`) | NATS (`training.job.*`) |
| Владеет продовыми весами | Читает (inference only) | Пишет (создаёт новые артефакты) |

## 2. Model Runtime (C++/CUDA)

### 2.1 Структура репозитория

```
sovalune-model-runtime/
├── CMakeLists.txt
├── src/
│   ├── engine/            # обёртка над inference backend (llama.cpp-подобный либо TensorRT-LLM — выбор ниже)
│   ├── tool_calling/       # парсинг instruction-tool вызовов из вывода модели
│   ├── nats_bridge/        # C++ NATS клиент, публикация/подписка на subjects
│   ├── tokenizer/          # токенизатор модели (нужен и здесь, и в Rust для Context Weaver — см. 2.4)
│   └── main.cpp
├── bindings/
│   └── ffi/                # C ABI слой, если Rust будет напрямую линковать (опционально, см. 2.5)
└── tests/
```

### 2.2 Выбор инференс-бэкенда

Решение фиксируется на этапе реализации, но требования:

- Поддержка GGUF-подобного квантованного формата, чтобы 8B модель
  реально влезала в потребительский/недорогой GPU (квантование
  Q4-Q8 диапазон).
- Поддержка constrained/structured generation (грамматики или
  JSON-schema-guided decoding) — это обязательно для надёжного
  tool-calling: модель не должна "почти правильно" форматировать вызов
  инструмента, вывод должен грамматически гарантированно быть валидным
  JSON по схеме из `sovalune-instruction-sdk`.
- Кандидаты для оценки на этапе реализации: llama.cpp (простота,
  хорошая GGUF-экосистема) vs TensorRT-LLM (выше throughput, сложнее
  интеграция, требует NVIDIA стек плотнее). Итоговый выбор — по
  результатам замера на целевом железе.

### 2.3 Tool-calling loop (обязательный алгоритм)

1. Модель генерирует токены; парсер (`tool_calling/`) детектирует
   начало structured tool-call блока (по грамматике, не по эвристике
   на сырых токенах).
2. Генерация приостанавливается, вызов публикуется в NATS
   (`tools.call.<tool_name>`) с `request_id` и `cycle_id`
   (если это часть Self-Learning Loop).
3. Runtime ждёт ответ на `tools.result.<request_id>` с таймаутом
   (конфигурируем, обязателен — модель не должна зависать вечно ждя
   инструмент).
4. Результат инструмента инжектируется обратно в контекст модели по
   протоколу модели (tool-result message), генерация продолжается.
5. Максимальное число последовательных tool-call в одном ответе —
   конфигурируемый лимит (защита от циклов "инструмент → инструмент →
   инструмент" без прогресса).

### 2.4 Токенизатор — важное архитектурное требование

Rust Context Weaver (см. `03-vector-memory.md`, п. 4.2) должен считать
токены **тем же токенизатором**, что использует модель в Model Runtime
— иначе токен-бюджет будет неточным. Два варианта, выбор — на этапе
реализации:

- (a) Токенизатор реализован как чистый Rust крейт (если для выбранной
  модели существует совместимая Rust-реализация — напр. семейство
  `tokenizers` от HuggingFace для BPE-based моделей), используется и в
  Core, и как источник истины;
- (b) Токенизация выполняется через FFI-вызов в C++ (если требуется
  бинарная совместимость), Rust держит только тонкий биндинг.

Требование, а не рекомендация: **точность подсчёта токенов должна
быть 100%-но идентична реальному токенизатору модели**, приблизительные
эвристики ("1 токен ≈ 4 символа") недопустимы для продакшена, только
для самых ранних прототипов.

### 2.5 Dev mode (без GPU)

Для локальной разработки без CUDA — обязателен CPU fallback режим
(даже если медленный), чтобы фронтенд/бэкенд разработчики могли
работать без GPU-машины. Флаг `SOVALUNE_RUNTIME_MODE=cpu|cuda`.

## 3. Training Pipeline (Python)

### 3.1 Структура репозитория

```
sovalune-training/
├── pyproject.toml
├── sovalune_training/
│   ├── jobs/
│   │   ├── adapter_tune.py    # LoRA/adapter дообучение по задаче из Self-Learning Loop
│   │   └── eval_only.py       # прогон verified-корпуса без изменения весов
│   ├── datasets/               # загрузка/подготовка датасетов из экспортов Core
│   ├── nats_worker.py          # слушает training.job.request, публикует training.job.result
│   └── artifact_store.py       # запись артефактов (адаптеры, метрики) в объектное хранилище
└── tests/
```

### 3.2 Требования

- Никакого прямого доступа к продовой Sovalune Storage — входные
  данные приходят только как экспортированные датасеты (см.
  `01-architecture.md`, раздел 5).
- Каждый job — воспроизводим: фиксируется seed, версия датасета, версия
  базовой модели/адаптера, из которого стартовали.
- Артефакты (веса адаптеров) версионируются и никогда не перезаписывают
  предыдущую версию — только новая запись с ростом версии, чтобы
  Self-Learning Loop мог откатиться при регрессии.

## 4. Instruction Tools — реестр (первая версия)

Полная схема каждого инструмента — в `sovalune-instruction-sdk`
(JSON Schema), здесь — минимальный обязательный набор на старте:

| Инструмент | Назначение |
|---|---|
| `memory_search` | Поиск в Vector Memory (см. `03-vector-memory.md`, раздел 7) |
| `memory_write` | Запись новой raw-записи в память |
| `run_tests` | Запуск тестов над сгенерированным кодом (в изолированном окружении, не на хосте Model Runtime) |
| `web_search` / `docs_search` | Поиск источников для Self-Learning Loop (раздел `RESEARCHING`) |
| `code_execute` | Выполнение кода в песочнице для практики/теста (см. ниже, безопасность) |

### 4.1 Безопасность выполнения кода

`run_tests` и `code_execute` **обязаны** выполняться в изолированном
контейнере/sandbox с ограничением по CPU/памяти/времени и без сетевого
доступа по умолчанию — Model Runtime никогда не выполняет
сгенерированный код в собственном процессе или на хост-системе.
