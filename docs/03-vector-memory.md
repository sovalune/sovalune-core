# Vector Memory + Context Weaver — детальное ТЗ

Крейт: `sovalune-vector-memory` (git submodule).

**Реализация памяти:** Supabase Postgres + pgvector (форк `sovalune-vector`).
Все операции с векторной памятью идут через `sovalune-storage-client` (SQLx)
поверх Supabase.

## 1. Назначение

Подсистема отвечает за две задачи, которые концептуально разные и не
должны смешиваться в одном модуле:

1. **Хранение и поиск** — эмбеддинги, семантический поиск, консолидация
   дублей знаний.
2. **Context Weaver** — решает, *что именно* и *в каком объёме*
   попадёт в промпт модели на конкретный запрос, укладываясь в
   токен-бюджет.

## 2. Модель данных памяти (концептуально; DDL — в `07-storage-schema.md`)

Память — не плоский список фактов. Три уровня:

| Уровень | Что это | Пример |
|---|---|---|
| `raw_memory` | Сырые записи — то, что модель узнала/сделала | "Пользователь попросил рефакторинг функции X, тесты не прошли из-за Y" |
| `consolidated_knowledge` | Обобщённое знание, полученное из нескольких raw-записей | "В проекте Z принято соглашение об обработке ошибок через Result<T, AppError>" |
| `verified_fact` | Знание, прошедшее цикл верификации Self-Learning Loop | "Функция `foo()` в библиотеке `bar` принимает аргумент в миллисекундах, не секундах — подтверждено официальной документацией v2.3" |

Каждая запись имеет:
- `embedding: vector(N)` (размерность N фиксируется под выбранную
  embedding-модель, см. раздел 5)
- `content: text`
- `metadata: jsonb` (источник, timestamp, project_id, confidence_score)
- `tier: raw | consolidated | verified`
- `decay_score: float` — для механизма "забывания" нерелевантного (см.
  раздел 6)

## 3. API крейта (внутренний, вызывается из `sovalune-api` и из
Self-Learning Orchestrator)

```rust
pub trait VectorMemoryStore {
    async fn insert_raw(&self, entry: RawMemoryEntry) -> Result<MemoryId>;
    async fn search(
        &self,
        query: &str,
        filter: MemoryFilter,
        top_k: usize,
    ) -> Result<Vec<ScoredMemory>>;
    async fn consolidate(&self, candidate_ids: &[MemoryId]) -> Result<MemoryId>;
    async fn promote_to_verified(&self, id: MemoryId, evidence: Evidence) -> Result<()>;
    async fn decay_tick(&self) -> Result<usize>; // фоновая задача, см. раздел 6
}
```

`MemoryFilter` включает: `project_id`, `tier` (можно искать только
среди verified), `min_confidence`, временное окно.

## 4. Context Weaver

### 4.1 Задача

Вход: запрос пользователя + `project_id` + текущая история диалога.
Выход: финальный промпт-контекст, вписанный в жёсткий токен-бюджет.

### 4.2 Алгоритм (обязательные шаги, порядок фиксирован)

1. Semantic search в `verified_fact` и `consolidated_knowledge` (raw
   подключается только если явно запрошено — по умолчанию raw не
   инжектируется, чтобы не тащить в контекст шум).
2. Ранжирование результатов: `score = similarity * confidence_weight *
   recency_weight`. Веса конфигурируемы, не хардкодятся.
3. Жадное заполнение токен-бюджета по убыванию score, с подсчётом
   токенов через токенизатор модели (не приблизительно по символам —
   см. `05-model-runtime.md` про экспорт токенизатора в Rust через
   FFI/биндинг, либо использование чистого Rust токенизатора,
   совместимого с моделью).
4. **Обязательное сжатие, а не просто отсечение.** Если запись не
   помещается целиком, а токен-бюджет ещё не исчерпан — Context Weaver
   не обрезает текст механически, а помечает запись как кандидата на
   summarization (короткая суммаризация выполняется либо заранее при
   consolidate(), либо через отдельный лёгкий вызов модели — это
   architectural decision, который фиксируется при реализации, но
   ключевое правило: **никогда не отправлять модели обрубленный
   на середине смысловой единицы текст**).
5. Финальный контекст размечается по секциям (`<verified_facts>`,
   `<recent_context>`, `<project_conventions>`), чтобы модель могла
   визуально/структурно различать источник достоверности.

### 4.3 Token Budget

- Конфигурируемый параметр `max_memory_tokens`, отдельный от общего
  контекстного окна модели. Остальной контекст (системный промпт,
  история диалога, ответ) получает свою долю бюджета — общая сумма
  никогда не должна приближаться к лимиту окна модели без запаса
  (рекомендация: держать резерв не менее 15% окна на генерацию ответа).
- Бюджет памяти по умолчанию — не более 25% от общего контекстного
  окна модели. Значение конфигурируемо на уровне проекта.

## 5. Эмбеддинг-модель

- Решение фиксируется при реализации, но требование: эмбеддинг должен
  генерироваться **локально** (внутри Model Runtime или отдельным
  лёгким сервисом), не через внешний платный API — это противоречит
  идее автономного 8B-стека. Кандидаты для выбора на этапе реализации:
  компактные open-weight embedding-модели (класс BGE/E5/GTE small
  variants), финальный выбор — по бенчмарку на реальных данных проекта.
- Размерность вектора фиксируется в схеме БД под выбранную модель —
  смена модели требует миграции с реэмбеддингом всего корпуса
  (это дорогая операция, поэтому выбор модели должен быть осознанным
  на раннем этапе, не "поменяем потом легко").

## 6. Decay / забывание

- Фоновая задача (`decay_tick`), запускается по расписанию через NATS
  (`memory.decay.tick`, публикуется cron-подобным планировщиком в
  Core).
- `decay_score` снижается со временем для `raw_memory`, если запись не
  была ни разу использована в поиске и не консолидирована.
- Записи с `decay_score` ниже порога не удаляются физически сразу —
  переводятся в `archived = true` (soft-delete), физическая очистка —
  отдельная ручная/периодическая операция. **Verified facts никогда не
  подвергаются decay** — только явному пересмотру через новый цикл
  верификации, если появляется противоречащая информация.

## 7. Instruction Tool: доступ модели к памяти

Модель (в Model Runtime) вызывает память не напрямую, а через
Instruction Tool, описанный в `sovalune-instruction-sdk`:

```json
{
  "tool": "memory_search",
  "arguments": {
    "query": "string",
    "tier": "verified_fact | consolidated_knowledge | raw_memory",
    "top_k": 5
  }
}
```

Ответ инструмента — компактный список `ScoredMemory` в JSON, тоже
ограниченный по объёму (см. `08-api-contracts.md` для точного формата).
