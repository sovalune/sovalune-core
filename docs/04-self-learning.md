# Self-Learning Loop — детальное ТЗ

Крейт: `sovalune-self-learning` (git submodule). Оркестрация — в Rust;
тяжёлые вычисления (обучение) делегируются в Python Training Pipeline
через NATS.

## 1. Принцип

Если модель ошиблась (или её решение не прошло проверку), система не
просто корректирует ответ — она проходит полный верифицированный цикл,
прежде чем **повторно** пытаться решить исходную задачу пользователя.
Цель — чтобы исправление было основано на подтверждённом источнике, а
не на "модель угадала другой вариант".

## 2. Стадии цикла (жёстко фиксированный порядок, каждая — отдельное
состояние в БД, персистентное)

```
DETECTED → RESEARCHING → VERIFYING → PRACTICING → TESTING → APPLYING → COMPLETED
                                                                  │
                                                                  └──► FAILED (если не удалось пройти стадию N раз)
```

### 2.1 `DETECTED` — обнаружение ошибки

Триггеры (любой из):
- Явный негативный фидбек пользователя.
- Автоматический тест/линтер/компилятор вернул ошибку на результат
  модели (для задач, где есть объективная проверка — код, конфиги).
- Self-critique шаг самой модели (модель сама помечает низкую
  уверенность в ответе).

Запись создаётся в таблице `learning_cycles` (см.
`07-storage-schema.md`) со статусом `DETECTED` и ссылкой на исходную
задачу/сообщение.

### 2.2 `RESEARCHING` — поиск источников

- Instruction Tool `web_search` / `docs_search` (если подключено —
  границы и разрешённые источники конфигурируются на уровне проекта,
  не хардкодятся в коде) либо поиск во `verified_fact` памяти других
  проектов (если применимо и разрешено политикой изоляции данных).
- Все найденные источники сохраняются как `evidence` записи, связанные
  с циклом — **не** сразу в память, а в промежуточную таблицу, пока не
  пройдена верификация.
- Лимит: максимум N источников (конфигурируемо, дефолт 5) и таймаут на
  стадию — если за отведённое время источники не найдены, цикл уходит
  в `FAILED` с причиной `NO_SOURCES_FOUND`, не зависает бесконечно.

### 2.3 `VERIFYING` — сверка источников

- Источники сверяются друг с другом на непротиворечивость.
- Если источники противоречат друг другу — приоритет по
  конфигурируемой иерархии доверия (например: официальная документация
  > верифицированные записи собственной памяти > общий веб-поиск).
- Результат стадии: либо согласованный вывод с `confidence_score`,
  либо переход в `FAILED` (`SOURCES_CONTRADICT` /
  `INSUFFICIENT_CONFIDENCE`) если согласованности достичь не удалось.
- **Порог confidence_score, необходимый для перехода дальше —
  конфигурируемый параметр, не зашитый в код.**

### 2.4 `PRACTICING` — практика на синтетических примерах

- Формируется набор небольших синтетических задач/тестов, изолированных
  от реальной задачи пользователя, где применяется новое знание.
- Это НЕ полноценное дообучение весов на этой стадии — это может быть:
  дополнительные few-shot примеры в промпте на пробных прогонах, либо
  (если конфигурация проекта это разрешает) лёгкий LoRA/adapter прогон
  через Python Training Pipeline на небольшом количестве шагов.
  Выбор механизма — architectural decision на этапе реализации, но
  требование: **эта стадия не должна модифицировать продовые веса
  модели напрямую**, только адаптеры/промпт-артефакты, которые потом
  проходят TESTING.

### 2.5 `TESTING` — объективная проверка

- Прогон синтетических тестов из `PRACTICING` + (если применимо)
  регрессионный прогон на наборе ранее verified фактов — новое знание
  не должно ломать старое.
- Порог прохождения — конфигурируемый (`min_pass_rate`).
- Провал → назад в `RESEARCHING` (retry) с ограничением на число
  повторов цикла (конфигурируемо, дефолт 3), после чего — `FAILED`.

### 2.6 `APPLYING` — применение к реальной задаче

- Только после успешного `TESTING` система пытается заново решить
  исходную задачу пользователя, теперь с новым знанием, доступным
  через Vector Memory (`promote_to_verified` вызывается ПЕРЕД этой
  стадией, чтобы Context Weaver мог его подхватить обычным путём).

### 2.7 `COMPLETED`

- Полная цепочка (evidence → verification → test results → итоговый
  ответ) сохраняется как аудируемая запись. Пользователю в интерфейсе
  доступна возможность посмотреть весь путь, которым система пришла к
  исправленному ответу (важно для доверия — см. `06-frontend.md`,
  визуализация Self-Learning Loop).

## 3. Гарантии и ограничения (обязательны к реализации)

- **Идемпотентность**: повторный запуск обработчика стадии для одного
  и того же `cycle_id` не должен создавать дублирующиеся evidence
  записи — обработчики стадий проверяют текущее состояние перед
  действием.
- **Наблюдаемость**: каждый переход стадии публикует событие в NATS
  (`learning.cycle.stage_changed`) — Frontend может показывать живой
  прогресс.
- **Изоляция по проектам**: цикл, запущенный в контексте проекта A, не
  промотирует знания в `verified_fact` для проекта B без явной
  кросс-проектной политики (по умолчанию — выключено).
- **Circuit breaker**: если для одного проекта происходит слишком
  много `FAILED` циклов подряд (порог конфигурируем) — система
  приостанавливает автозапуск новых циклов и требует ручного review,
  чтобы не тратить ресурсы на систематически нерешаемую проблему.

## 4. Взаимодействие с Python Training Pipeline

- Оркестратор в Rust НЕ содержит ML-кода. Он публикует задачу в NATS
  (`training.job.request`) с чётким контрактом (датасет, тип операции
  — "adapter_tune" / "eval_only", лимит шагов/времени).
- Python сервис слушает этот subject, выполняет работу, публикует
  результат (`training.job.result`) со ссылкой на артефакт (путь к
  адаптеру/весам в объектном хранилище) и метриками.
- Формат задачи и результата — фиксируется в `08-api-contracts.md`.

## 5. Что явно НЕ входит в scope этого модуля

- Полное переобучение базовой модели с нуля — это ручной, оффлайн
  процесс, управляемый напрямую через `sovalune-training`, не через
  автоматический Self-Learning Loop.
- Автоматическое разворачивание нового адаптера в прод без review —
  на первом этапе продукта это ручное подтверждение (флаг
  `auto_promote_adapter`, по умолчанию `false`).
